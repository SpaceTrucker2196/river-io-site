The label is not the control

Three approval gates failed on 16 November 2026. Each one trusted a label, a scope or a summary instead of a check.

This brief covers 15 to 17 November 2026. We found three new items, all dated 16 November. We also add one research paper from 11 November that we did not cover before. Each new item is about an approval gate. An approval gate is the check that decides if an agent action can run.

In each case, the gate trusted something that was not a check. One gate trusted a label. One gate trusted a token scope. One report trusted the agent's own summary.

A read-only label let a write run without approval

AWS published Security Bulletin 2026-184-AWS on 16 November 2026. It covers CVE-2026-126816 in the AWS Pricing MCP Server. MCP is the Model Context Protocol. It connects an agent to tools.

The server has a tool named generate_cost_report. The tool accepted absolute paths and ../ sequences in its output path. It could therefore write files outside its output folder.

The tool also had a read-only annotation. An annotation is a hint that the tool author attaches to a tool. Some MCP clients approve read-only tools automatically. Those clients could run this tool with no human check.

An actor who can influence the agent could use this to write files. Prompt injection is one way to influence an agent. Prompt injection is text that an agent reads and then follows as an instruction.

Version 1.0.31 of awslabs.aws-pricing-mcp-server fixes the issue. The older cost-analysis-mcp-server package is deprecated and gets no fix. AWS gives two workarounds. Remove the tool from auto-approve. Do not pass untrusted content to the agent.

An annotation is a claim by the tool author. It is not a control.

A token scope did not limit the token

The first row is the important one for a software factory. The scope name said MCP. The server let the token act like a maintainer. An agent that can approve and merge is an agent that can ship.

One approval, two writes

A developer posted a bug report on the OpenAI Developer Community on 16 November 2026. The report is about the Responses API. OpenAI has not confirmed the bug. OpenAI Support replied that it is “looking into this issue.”

The setup offers a read tool, a write tool and programmatic tool calling. Read-only tools are approved automatically. The developer approves one write. The same response then continues into a program that only reads.

The MCP server logged a write, a read, and a second write. Both writes had the same approval ID and the same arguments. The model's final message said that one write happened.

Community members suggested three workarounds. Split the approval turn from the read. Add a required idempotency key to each write tool. An idempotency key is a unique value that lets the server ignore a repeat of the same request. Also check for duplicate approval IDs on the client.

The lesson is direct. One approval must mean one execution. Count side effects from the server log, not from the agent's summary.

A test that must fail first

Vahid Haratian, Atakan Akar and Eray Tüzün submitted a preprint to arXiv on 11 November 2026. A preprint has not had peer review. The paper is “ADAPT: Agentic Diff-Aware Patch Testing for Pull Requests”.

In ADAPT, an agent reads the diff of a pull request. It writes unit tests that target the changed behavior. A tool then runs each test on the old code and on the new code. A useful test fails on the old code and passes on the new code. This is a fail-to-pass test.

Setup (426 pull requests)Fail-to-pass rate
ADAPT with GPT-5-mini89.9% (383)
ADAPT with GPT-4o62.0% (264)
BLAST, earlier method35.4% (151)

Our 15 November brief said that code review is now the slow step. A fail-to-pass test gives the reviewer a fast, mechanical signal. It does not replace review.

What it means for the River.io Software Factory

Our agent harness will approve tools by name only. It will not trust a read-only annotation. Every tool that takes a path gets tests for absolute paths, ../ and symbolic links. This is test-driven development, and it needs no third-party dependency.

Each agent write action gets an idempotency key. The key is the issue number plus a step name. The harness checks the key before it acts. We count actions from the GitHub API and the git log, not from the agent's report. We will add a METRICS.md row for duplicate actions that the key blocks.

The agent token never gets merge rights. Branch protection on main requires a human review. We will test this. The agent token will try a merge in a sandbox repo, and the merge must fail.

CI will run fail-to-pass checks on agent pull requests. Each new test runs on the base commit and must fail. It then runs on the head commit and must pass. A test that passes on both commits is not evidence. The native test runner in each repo does this work.

CareTime, TimeForCare and MaterialsAndPractices handle regulated data. They stay at human-gated autonomy. No write tool in these repos gets auto-approve.

We will test the idempotency key and the fail-to-pass check on MeowPassword, weathergalactic or sloth for two weeks. We will publish the counts.
