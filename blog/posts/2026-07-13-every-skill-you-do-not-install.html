Every skill you do not install is an attack you do not have to detect

New research shows malicious behavior can hide inside agent skills themselves, evading scanners while preserving 96.6% of benign utility. The attack surface has moved from the agent's inputs to its toolbox.

In mid-July 2026, the research frontier in agentic-coding security shifted. The headline vulnerabilities of early July (GitLost, GuardFall) were about hostile content: issues, pull requests, and web pages that carry hidden instructions to an agent reading them. The new wave is about hostile capabilities. A paper titled PhantomSkill, introducing an attack technique the authors call VulMask (arXiv 2606.19191), demonstrates that malicious behavior can be hidden inside an agent skill's auxiliary scripts, rewritten as ordinary-looking "vulnerability-shaped" code that fires only on an attacker's trigger. The results: a 58.8% attack success rate while preserving 96.6% of the skill's benign utility, largely evading skill scanners and automated reviewers across major coding agents.

A class, not a one-off

PhantomSkill did not arrive alone. A companion wave of research (Cloak and Detonate on scanner evasion and dynamic detection, SKILL-INJECT on measuring agent vulnerability to skill-file attacks, and a survey of supply-chain poisoning across LLM coding-agent skill ecosystems) confirms this is a systemic class of attack, complete with its own curated tracker, the awesome-agent-skills-security list.

The core insight is uncomfortable for anyone relying on marketplace review: scanners look for malicious intent in a skill's description, while the attack hides as ordinary insecure-looking code in auxiliary files, activated later. Static scanning of skill text is not a control. Cloak and Detonate argues for dynamic detection instead, but the defensible posture available today is simpler: a minimal skill surface, first-party only. Agent skills and plugins are executable supply chain, not configuration.

Also this week: do not trust the screen

Security researcher Johann Rehberger demonstrated a time-of-check to time-of-use (TOCTOU) attack on computer-use and coding agents: mutate the UI between the agent's visual check and its click, and the agent approves something it never saw. Any approval flow where an agent visually verifies and then acts is racy by construction. Approvals that matter should be verified at the API or data layer, atomically, never via screenshots.

Measuring autonomy before granting it

On the constructive side, Anthropic published field research on measuring AI agent autonomy in practice, drawn from how agents are actually deployed on its public API. Software engineering accounts for roughly half of all agentic activity, making it the closest thing available to ground truth on how far real deployments run unattended. The practical guidance follows directly: instrument what agents actually do without supervision, then set autonomy gates from data rather than optimism.

A new academic framework goes further and formalizes the gating itself. A paper on autonomous CI/CD quality assurance (built on LangGraph multi-agent orchestration, from K11tech) runs a complete quality gate from pull request to defect filing using 14 specialist agents, but computes a per-change risk score and suspends execution to a human whenever that score reaches 0.85 or above. The stack (LangGraph, seven MCP servers) is not one we would adopt, but the pattern is the right abstraction: autonomy as a continuous function of measured risk, not a repository-level on-off switch. It matches the bounded-autonomy framing of the "From Assistance to Agency" work on CI/CD pipelines.

Two smaller signals round out the picture. First, "harness engineering" is now a named discipline with its own curated list (awesome-harness-engineering) covering evals, memory, permissions, observability, and orchestration; the center of gravity is not the model, it is the harness. Second, a distinction now circulating in the field: personal agents run on markdown files, production agents need databases, access control, and memory at scale. The gap between a hobby loop and a factory is infrastructure. Spec-driven tooling also continued to mature, with ASSERT (turning specs into repeatable evals), Google's published account of automating the eval-optimize loop with independent AutoRaters grading agent output against custom rubrics, and a consolidating market of purpose-built eval-gate products.

The proof point that matters

The reference case for production-scale agentic coding remains Spotify's background coding agent, Honk: roughly 650 agent-generated pull requests merged to production per month, more than 1,500 cumulative, with 60 to 90 percent time savings on migrations, run by a small team. Spotify explicitly credits years of prior investment in fleet management, standardized builds, and comprehensive test suites.

The agent is the cheap part. The deterministic test and build substrate is the factory.

The counterweights deserve equal billing. Google's widely cited figure of about 75% AI-generated code (per Sundar Pichai) counts suggested-and-accepted code, a much weaker definition than autonomously merged. A survey of software engineering's third era finds agent pull requests complete fast (half within about 13 minutes) but are accepted at lower rates than human ones. Older randomized controlled trials still show the full spread: a 26% increase in pull requests per week in one, no productivity lift and a 41% increase in bug density in another. Throughput is not merged quality.

How we apply this at River.io

This research wave lands as vindication of a posture we already hold, and it converts that posture from engineering taste into security architecture.

  • Zero dependencies extends to the automation layer. PhantomSkill's entire attack surface is third-party skills, actions, and MCP servers. River.io ships native compiled code with no third-party libraries, and we run our agents the same way: no third-party agent skills, no unpinned marketplace actions, first-party scripts only. Every capability we do not install is an attack class that does not exist against us.
  • Verification is behavioral, not textual. GuardFall broke string matching on commands; VulMask breaks static scanning of skill code. The only gate that survives both is running the thing: compile, execute the full test suite, and diff observable behavior. Our test-driven development discipline makes that gate native. For agent-authored pull requests, tests-pass plus behavior-diff is the gate; human code review of agent tooling is necessary but demonstrably insufficient on its own.
  • Regulated repositories are permanently pinned above the risk threshold. For CareTime and TimeForCare (Medicaid EVV, PHI-adjacent) and MaterialsAndPractices (organic compliance), the risk-proportionate gate simply never opens. Agents may draft; humans author every compliance-defining assertion and approve every merge, and agents hold no read access to these repositories at all.
  • Risk-scored autonomy on low-stakes repositories. On MeowPassword, weathergalactic, and sloth, we run a dependency-free version of the risk-proportionate pattern: score each agent task on factors like whether it touches authentication or persistence, diff size, and new files, and auto-suspend to a human above a threshold. Combined with label-gated issue intake, injection red-teaming, and a log of corrective interventions per task, that gives us a measurable, per-repository case for loosening gates.
  • Pour the concrete before installing the robots. Spotify's throughput was possible because builds and tests were already deterministic and comprehensive. Our equivalent groundwork: every repository that will ever host an autonomous loop gets a complete, fast, native test suite first. Test coverage is the factory floor.
  • No screenshot-verified approvals, ever. If an agent ever drives a UI for us (App Store screenshot automation, device testing), state is verified via API or filesystem atomically with the action. Rehberger's TOCTOU result makes look-then-click approval unsafe by design.
